\section{Introduzione}
\subsection{Obiettivo del progetto}
S.A.G.E. (Sistema di Analisi e Gestione Economica) è un'applicazione desktop per la gestione delle finanze personali di uno studente universitario. Il sistema supporta la registrazione di entrate e spese, la classificazione dei movimenti, la definizione di budget e la consultazione di riepiloghi utili per monitorare l'andamento economico nel tempo.

L'obiettivo del progetto non è soltanto realizzare un'applicazione funzionante, ma documentare l'intero ciclo di progettazione di una base di dati: analisi dei requisiti, modellazione concettuale, traduzione logica, implementazione SQL e collegamento a un programma Java tramite JDBC.

\subsection{Descrizione generale del sistema}
S.A.G.E. è progettato come sistema multiutente. Ogni studente accede con le proprie credenziali e visualizza soltanto i dati collegati alla propria email. Il portafoglio personale comprende transazioni, categorie, fonti, tag, budget, documenti digitali e modelli di spese ricorrenti.

L'applicazione è realizzata in Java Swing e comunica con un database MySQL tramite JDBC. La logica applicativa è organizzata in livelli: le classi del package \texttt{model} rappresentano il dominio, i DAO incapsulano le query SQL, i controller coordinano i casi d'uso e le classi del package \texttt{view} compongono l'interfaccia grafica.

\subsection{Ambito del sistema}
L'ambito del progetto comprende:
\begin{itemize}
    \item gestione individuale del portafoglio economico personale;
    \item registrazione di spese ed entrate;
    \item classificazione delle spese tramite categorie e tag;
    \item classificazione delle entrate tramite fonti;
    \item definizione di budget mensili e budget specifici per categoria;
    \item gestione di spese ricorrenti come modelli astratti;
    \item associazione di documenti digitali alle spese;
    \item visualizzazione di riepiloghi e statistiche.
\end{itemize}
Non rientrano nell'ambito del sistema la condivisione di conti tra utenti, la sincronizzazione cloud dei file allegati e l'integrazione con servizi bancari esterni.

\subsection{Utenti e ruoli previsti}
Il sistema prevede due ruoli:
\begin{itemize}
    \item \textbf{Utente}: registra transazioni, consulta il proprio portafoglio, gestisce categorie personali, definisce budget e associa documenti alle spese.
    \item \textbf{Amministratore}: gestisce elementi di sistema, come categorie, fonti e tag globali. L'amministratore può accedere solo a statistiche aggregate e non ai dettagli finanziari personali degli utenti.
\end{itemize}

\subsection{Tecnologie utilizzate}
\begin{itemize}
    \item \textbf{DBMS}: MySQL.
    \item \textbf{Ambiente locale}: XAMPP, utilizzato per avviare il server MySQL locale e per amministrare il database tramite phpMyAdmin durante sviluppo e test.
    \item \textbf{Linguaggio applicativo}: Java.
    \item \textbf{Interfaccia}: Java Swing.
    \item \textbf{Connessione al database}: JDBC con MySQL Connector/J.
    \item \textbf{Architettura}: applicazione desktop 2-tier con accesso diretto al DBMS.
\end{itemize}

\subsection{Scelte progettuali preliminari}
Le scelte iniziali più rilevanti sono:
\begin{itemize}
    \item isolamento dei dati tramite email dell'utente autenticato;
    \item distinzione tra elementi globali di sistema ed elementi personali;
    \item gestione opzionale del budget, che non blocca l'inserimento di nuove spese;
    \item memorizzazione dei documenti digitali tramite percorso file, evitando di salvare il contenuto binario direttamente nel database.
\end{itemize}
La scelta sui documenti riduce il peso del DBMS e semplifica le operazioni JDBC. Presenta però un limite noto: se l'applicazione viene usata da un altro dispositivo collegato allo stesso database, un percorso locale potrebbe non essere più valido. Questa criticità viene considerata tra i possibili sviluppi futuri.

\section{Analisi dei requisiti}
\subsection{Requisiti in linguaggio naturale}
Il sistema deve permettere a uno studente di registrare e monitorare i propri movimenti economici. Ogni transazione deve avere data, importo e descrizione. Una spesa deve essere associata a una categoria e può avere tag e documenti digitali; un'entrata deve essere associata a una fonte. L'utente deve poter definire budget mensili riutilizzabili, globali o opzionalmente legati a una categoria. Il sistema deve inoltre supportare spese ricorrenti come modelli da cui generare movimenti effettivi.

\subsection{Specifiche ristrutturate}
\begin{itemize}
    \item R1: autenticare utenti e amministratori.
    \item R2: registrare spese ed entrate con data, importo e descrizione.
    \item R3: associare ogni spesa a una categoria e ogni entrata a una fonte.
    \item R4: associare tag e documenti digitali alle spese.
    \item R5: gestire budget mensili e budget per categoria.
    \item R6: gestire spese ricorrenti come modelli astratti.
    \item R7: filtrare ogni dato operativo tramite l'email dell'utente autenticato.
    \item R8: consentire all'amministratore solo operazioni su cataloghi globali e statistiche aggregate.
\end{itemize}

\subsection{Glossario dei termini essenziali}
\begin{itemize}
    \item \textbf{Utente}: studente identificato da email, nome, cognome, password e ruolo.
    \item \textbf{Transazione}: movimento economico generico, distinto in spesa o entrata.
    \item \textbf{Categoria}: classificazione principale di una spesa.
    \item \textbf{Fonte}: origine di un'entrata.
    \item \textbf{Tag}: etichetta trasversale che consente classificazioni aggiuntive.
    \item \textbf{Budget}: limite di spesa mensile collegato a un utente e, opzionalmente, a una categoria; per lo stesso ambito esiste una sola configurazione.
    \item \textbf{Documento}: riferimento digitale a uno scontrino o a una fattura associata a una spesa.
    \item \textbf{Spesa ricorrente}: modello da cui generare spese periodiche.
\end{itemize}

\subsection{Classi di utenza e viste del sistema}
\begin{itemize}
    \item \textbf{Studente}: utilizza dashboard, transazioni, budget, documenti, categorie personali e report.
    \item \textbf{Amministratore}: gestisce cataloghi globali e consulta indicatori aggregati.
\end{itemize}
La vista studente è centrata sul portafoglio personale. Ogni schermata applicativa riceve l'utente corrente e usa la sua email come chiave di sessione.

\subsection{Elenco delle operazioni principali}
\begin{itemize}
    \item Login e apertura della dashboard personale.
    \item Inserimento di una spesa con categoria, tag opzionali e documento opzionale.
    \item Inserimento di una entrata con fonte.
    \item Consultazione dei movimenti per periodo.
    \item Definizione o aggiornamento di un budget.
    \item Associazione e apertura di un documento digitale.
    \item Creazione di categorie, fonti e tag personali.
    \item Consultazione di riepiloghi e statistiche aggregate.
\end{itemize}

\subsection{Vincoli espliciti e impliciti}
\begin{itemize}
    \item Ogni query sui dati personali deve filtrare per email dell'utente autenticato.
    \item Una spesa deve avere una categoria e non deve avere una fonte.
    \item Una entrata deve avere una fonte e non deve avere una categoria.
    \item I tag sono associabili solo alle spese.
    \item I documenti sono associabili solo alle spese.
    \item Il budget è opzionale e non impedisce l'inserimento di movimenti.
    \item Il contenuto dei documenti non è salvato nel database; viene salvato solo il riferimento al file.
\end{itemize}

Le scelte sono guidate da tre criteri: isolamento dei dati per utente, semplicità di interrogazione e coerenza con l'applicazione Java.

\subsection{Raffinamenti dello schema}
\subsubsection{Gerarchia delle transazioni}
Nel dominio esistono due sottotipi di transazione: spesa ed entrata. La specializzazione è totale ed esclusiva: ogni transazione è necessariamente una spesa o una entrata, e non può essere entrambe. Nel modello logico questa gerarchia è collassata in \textsc{TRANSIZIONE}, con l'attributo \texttt{TipoTransazione}. I vincoli CHECK garantiscono la coerenza: una spesa richiede \texttt{ID\_Categoria}, una entrata richiede \texttt{ID\_Fonte}.

\subsubsection{Elementi di sistema e personali}
\textsc{CATEGORIA}, \textsc{TAG} e \textsc{FONTE} sono modellati con una soluzione ibrida. Gli elementi globali hanno \texttt{is\_system = TRUE} e nessun proprietario; gli elementi personali hanno \texttt{is\_system = FALSE} e sono collegati a un utente. Le query applicative mostrano a uno studente sia gli elementi globali sia quelli personali.

\subsubsection{Reificazione del budget}
Il budget è modellato come entità autonoma collegata all'utente e a un ambito: globale oppure riferito a una categoria. Il sistema mantiene una sola configurazione per ciascun ambito e aggiorna il periodo di riferimento al mese corrente; in questo modo non vengono create copie gennaio, febbraio, marzo dello stesso budget. L'attributo \path{Totale_Speso_Attuale} è ridondante, ma serve a rendere efficiente la dashboard.

\subsubsection{Documenti digitali}
Il documento digitale è collegato a una spesa e contiene \texttt{Path\_File}, \texttt{Tipo\_File} e \path{Data_Acquisizione_Documento}. Il contenuto binario del file non è salvato nel DBMS.

Questa scelta riduce il peso del database e semplifica backup, query e codice JDBC. Il limite principale è la portabilità: spostandosi su un altro dispositivo, il percorso locale potrebbe non esistere. Una futura versione potrebbe usare path relativi sincronizzati oppure un attributo \texttt{LONGBLOB}, qualora la portabilità completa del documento attraverso il solo database diventasse un requisito prioritario.

\subsection{Vincoli non rappresentabili direttamente nello schema E/R}
Alcune regole richiedono vincoli SQL o controlli applicativi:
\begin{itemize}
    \item una categoria personale è visibile solo al proprietario;
    \item una spesa può usare solo categorie di sistema o categorie personali dell'utente;
    \item un documento può essere collegato solo a una spesa, non a una entrata;
    \item l'amministratore non deve visualizzare dettagli finanziari personali;
    \item l'inserimento di spesa, tag, documento e aggiornamento budget deve essere atomico.
\end{itemize}

\subsection{Dizionario di entità e associazioni}
Il dizionario riassume gli attributi principali:
\begin{itemize}
    \item \textsc{UTENTE}: Email, Password, Nome, Cognome, Ruolo.
    \item \textsc{TRANSIZIONE}: ID, TipoTransazione, Importo, Data, Descrizione, Email, Categoria/Fonte.
    \item \textsc{BUDGET}: ID, Importo\_Limite, Alert\_Soglia, Totale\_Speso\_Attuale, Periodo corrente, Categoria opzionale, Email; il vincolo su Email e categoria impedisce duplicati dello stesso budget.
    \item \textsc{DOCUMENTO}: ID, ID\_Transizione, Path\_File, Tipo\_File, Data\_Acquisizione\_Documento.
    \item \textsc{SPESA\_TAG}: associazione molti-a-molti tra spesa e tag.
\end{itemize}

\subsection{Operazioni di modifica ed eliminazione}
Le modifiche riguardano budget, categorie, fonti e tag, sia personali sia di sistema quando l'operazione è svolta dall'amministratore. Le eliminazioni devono rispettare i vincoli referenziali: ad esempio una categoria eliminata non deve lasciare riferimenti incoerenti nelle spese già registrate. La cancellazione di transazioni o documenti sfrutta le regole di integrità definite nello schema SQL.

\subsection{Operazioni di interrogazione}
\begin{itemize}
    \item elenco delle transazioni dell'utente per periodo;
    \item elenco di categorie, fonti e tag disponibili;
    \item elenco dei budget e relativo stato di superamento;
    \item elenco dei documenti associati alle spese dell'utente;
    \item elenco delle spese ancora prive di documento.
\end{itemize}

\subsection{Operazioni statistiche e amministrative}
Le statistiche includono totali mensili di spese ed entrate, rapporto percentuale tra spese ed entrate, budget superati e aggregazioni per categoria. L'amministratore deve utilizzare viste aggregate, evitando l'accesso a descrizioni, documenti o movimenti granulari degli utenti.

La navigazione parte normalmente da \textsc{UTENTE}, identificato dalla sessione. Le transazioni vengono raggiunte tramite \textsc{EFFETTUA} e sono collocate temporalmente tramite \textsc{AVVIENE}. Da una spesa si prosegue verso categoria, tag e documento; da una entrata verso la fonte. I budget sono raggiunti tramite \textsc{DEFINIZIONE} e \textsc{RELATIVO}, mentre \textsc{LIMITAZIONE} è presente soltanto per i budget specifici di categoria. Le spese ricorrenti sono raggiunte tramite \textsc{PIANIFICA} e collegate alla categoria mediante \textsc{TIPO\_RICORRENZA}.

Le ipotesi usate sono: dieci transazioni medie nella consultazione di un periodo, di cui otto spese e due entrate; un tag medio per spesa; un documento ogni dieci movimenti consultati; cinque budget mostrati nella dashboard, di cui quattro specifici per categoria. Per il monitoraggio non vengono rilette tutte le spese, perché si sfrutta la ridondanza \path{Totale_Speso_Attuale}. Nella generazione delle ricorrenze si considerano al massimo due budget aggiornabili: quello generale e quello della categoria.

\subsection{Analisi delle ridondanze}
L'attributo \path{Totale_Speso_Attuale} della relazione \textsc{BUDGET} è ridondante perché può essere ricavato sommando le spese presenti in \textsc{TRANSIZIONE}. La ridondanza viene mantenuta per ridurre il costo delle letture più frequenti della dashboard.

La coerenza viene garantita con due regole applicative:
\begin{itemize}
    \item quando viene inserita una spesa, l'inserimento della transazione, l'associazione di tag/documento e l'aggiornamento degli eventuali budget avvengono nella stessa transazione JDBC;
    \item quando un budget viene creato o aggiornato dopo spese già registrate, il valore iniziale viene calcolato con una query di aggregazione sulle transazioni esistenti.
\end{itemize}

In questo modo il budget rimane opzionale senza perdere consistenza: l'assenza di un budget non blocca la registrazione della spesa, mentre l'esistenza di un budget impone la sincronizzazione del suo totale ridondante.

\subsection{Raffinamento dello schema}
\subsubsection{Eliminazione delle gerarchie}
La gerarchia spesa/entrata viene eliminata collassando i sottotipi in \textsc{TRANSIZIONE}. La distinzione rimane espressa da \texttt{TipoTransazione}, mentre i vincoli CHECK controllano la presenza corretta di categoria o fonte.

\subsubsection{Eliminazione degli attributi composti}
Non sono presenti attributi composti significativi da scomporre ulteriormente. Nome e cognome dell'utente sono già separati; il periodo è rappresentato da mese e anno nella tabella \textsc{PERIODO}.

\subsubsection{Gestione degli attributi multivalore}
I tag associati a una spesa rappresentano un attributo multivalore. Vengono tradotti nella relazione \textsc{SPESA\_TAG}, con chiave primaria composta da \texttt{ID\_Transizione} e \texttt{ID\_Tag}.

\subsubsection{Scelta delle chiavi primarie}
L'email è scelta come chiave primaria di \textsc{UTENTE}, perché identifica direttamente la sessione applicativa. Le altre entità principali utilizzano identificatori numerici auto-incrementali per semplificare riferimenti e join.

\subsubsection{Traduzione delle associazioni}
Le associazioni 1:N sono tradotte tramite chiavi esterne. Le associazioni N:M, come quella tra spese e tag, sono tradotte tramite tabella ponte. I vincoli applicativi più specifici sono rafforzati tramite trigger e controlli SQL.

\section{Implementazione SQL}
\subsection{Script di creazione del database}
Gli script SQL consolidati sono \texttt{01\_schema\_completo.sql}, \texttt{02\_popolamento\_demo.sql}, \texttt{03\_migrazione\_database\_esistente.sql} e \texttt{04\_query\_operazioni.sql}.

Lo script \path{doc/sql/01_schema_completo.sql} crea da zero il database MySQL e seleziona lo schema prima di definire le relazioni. L'ordine di creazione segue le dipendenze referenziali: prima le entità indipendenti, poi quelle che importano chiavi esterne.

\begin{lstlisting}[caption={Creazione dello schema e delle tabelle UTENTE e PERIODO}]
DROP DATABASE IF EXISTS Schema_finale_del_relazionale_SAGE_Vista_ibrida_Raffinata;
CREATE DATABASE Schema_finale_del_relazionale_SAGE_Vista_ibrida_Raffinata;
USE Schema_finale_del_relazionale_SAGE_Vista_ibrida_Raffinata;

CREATE TABLE UTENTE (
    Email VARCHAR(255) NOT NULL,
    Password VARCHAR(128) NOT NULL,
    Nome VARCHAR(80) NOT NULL,
    Cognome VARCHAR(80) NOT NULL,
    Ruolo VARCHAR(10) NOT NULL DEFAULT 'UTENTE',
    CONSTRAINT PK_UTENTE PRIMARY KEY (Email),
    CONSTRAINT CK_UTENTE_RUOLO

);

CREATE TABLE PERIODO (
    ID_Periodo INT NOT NULL AUTO_INCREMENT,
    Mese TINYINT NOT NULL,
    Anno SMALLINT NOT NULL,
    CONSTRAINT PK_PERIODO PRIMARY KEY (ID_Periodo),
    CONSTRAINT UQ_PERIODO_MESE_ANNO UNIQUE (Mese, Anno),
    CONSTRAINT CK_PERIODO_MESE CHECK (Mese BETWEEN 1 AND 12),
    CONSTRAINT CK_PERIODO_ANNO CHECK (Anno >= 2000)
);
\end{lstlisting}

\subsection{Creazione delle tabelle}
Le tabelle di classificazione adottano la soluzione ibrida descritta nello schema concettuale. Il campo \texttt{is\_system} distingue gli elementi globali da quelli personali, mentre \texttt{Email\_Proprietario} è valorizzata soltanto per gli elementi creati dall'utente. \textsc{FONTE} e \textsc{TAG} sono costruite con la stessa struttura di \textsc{CATEGORIA}.

\begin{lstlisting}[caption={Tabella CATEGORIA per elementi di sistema e personali}]
CREATE TABLE CATEGORIA (
    ID_Categoria INT NOT NULL AUTO_INCREMENT,
    Nome VARCHAR(80) NOT NULL,
    Icona VARCHAR(255),
    is_system BOOLEAN NOT NULL DEFAULT FALSE,
    Email_Proprietario VARCHAR(255),
    CONSTRAINT PK_CATEGORIA PRIMARY KEY (ID_Categoria),
    CONSTRAINT FK_CATEGORIA_UTENTE
        FOREIGN KEY (Email_Proprietario)
        REFERENCES UTENTE (Email)
        ON UPDATE CASCADE
        ON DELETE CASCADE,
    CONSTRAINT CK_CATEGORIA_OWNER CHECK (
        (is_system = TRUE AND Email_Proprietario IS NULL)
        OR
        (is_system = FALSE AND Email_Proprietario IS NOT NULL)
    )
);
\end{lstlisting}

La relazione \textsc{TRANSIZIONE} realizza il collasso della gerarchia tra spesa ed entrata. Il vincolo \texttt{CK\_TRANSIZIONE\_COLLASSO} impone una categoria alle spese e una fonte alle entrate, escludendo le combinazioni incoerenti.

\begin{lstlisting}[caption={Tabella TRANSIZIONE e vincolo sul tipo di movimento}]
CREATE TABLE TRANSIZIONE (
    ID_Transizione INT NOT NULL AUTO_INCREMENT,
    TipoTransazione CHAR(1) NOT NULL,
    Importo DECIMAL(10,2) NOT NULL,
    Data DATE NOT NULL,
    Descrizione VARCHAR(255) NOT NULL,
    Email VARCHAR(255) NOT NULL,
    ID_Categoria INT,
    ID_Periodo INT NOT NULL,
    ID_Fonte INT,
    ID_Ricorrenza INT,
    CONSTRAINT PK_TRANSIZIONE PRIMARY KEY (ID_Transizione),
    CONSTRAINT FK_TRANSIZIONE_UTENTE FOREIGN KEY (Email)
        REFERENCES UTENTE (Email) ON UPDATE CASCADE ON DELETE CASCADE,
    CONSTRAINT FK_TRANSIZIONE_CATEGORIA FOREIGN KEY (ID_Categoria)
        REFERENCES CATEGORIA (ID_Categoria) ON UPDATE CASCADE ON DELETE SET NULL,
    CONSTRAINT FK_TRANSIZIONE_PERIODO FOREIGN KEY (ID_Periodo)
        REFERENCES PERIODO (ID_Periodo) ON UPDATE CASCADE ON DELETE RESTRICT,
    CONSTRAINT FK_TRANSIZIONE_FONTE FOREIGN KEY (ID_Fonte)
        REFERENCES FONTE (ID_Fonte) ON UPDATE CASCADE ON DELETE SET NULL,
    CONSTRAINT CK_TRANSIZIONE_TIPO CHECK (TipoTransazione IN ('S', 'E')),
    CONSTRAINT CK_TRANSIZIONE_IMPORTO CHECK (Importo > 0),
    CONSTRAINT CK_TRANSIZIONE_RICORRENZA CHECK (
        ID_Ricorrenza IS NULL OR TipoTransazione = 'S'
    ),
    CONSTRAINT CK_TRANSIZIONE_COLLASSO CHECK (
        (TipoTransazione = 'S' AND ID_Categoria IS NOT NULL AND ID_Fonte IS NULL)
        OR
        (TipoTransazione = 'E' AND ID_Categoria IS NULL AND ID_Fonte IS NOT NULL)
    )
);
\end{lstlisting}

\subsection{Definizione di chiavi primarie e chiavi esterne}

\subsection{Trigger e viste}
I trigger rafforzano i vincoli che devono valere anche al di fuori dell'applicazione Java. Il seguente controllo impedisce che una transazione utilizzi una categoria o una fonte non visibile all'utente e verifica la coerenza del collegamento con una ricorrenza.

\begin{lstlisting}[caption={Trigger di controllo sull'inserimento di una transazione}]
DELIMITER $$
CREATE TRIGGER trg_transizione_insert_check
BEFORE INSERT ON TRANSIZIONE
FOR EACH ROW
BEGIN
    IF NEW.TipoTransazione = 'S' AND NOT EXISTS (
        SELECT 1 FROM CATEGORIA C
        WHERE C.ID_Categoria = NEW.ID_Categoria
          AND (C.is_system = TRUE OR C.Email_Proprietario = NEW.Email)
    ) THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Categoria non valida per questo utente';
    END IF;

    IF NEW.TipoTransazione = 'E' AND NOT EXISTS (
        SELECT 1 FROM FONTE F
        WHERE F.ID_Fonte = NEW.ID_Fonte
          AND (F.is_system = TRUE OR F.Email_Proprietario = NEW.Email)
    ) THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Fonte non valida per questo utente';
    END IF;

    IF NEW.ID_Ricorrenza IS NOT NULL AND NOT EXISTS (
        SELECT 1 FROM SPESA_RICORRENTE SR
        WHERE SR.ID_Ricorrenza = NEW.ID_Ricorrenza
          AND SR.Email = NEW.Email
          AND SR.ID_Categoria = NEW.ID_Categoria
    ) THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Ricorrenza non coerente con la transazione';
    END IF;
END$$
DELIMITER ;
\end{lstlisting}

Le viste forniscono risultati già aggregati alla dashboard e alla vista amministrativa. In particolare, la vista amministrativa non espone le singole descrizioni né l'identità degli utenti, ma soltanto conteggi e somme per mese.

\begin{lstlisting}[caption={Vista delle statistiche aggregate per l'amministratore}]
CREATE VIEW v_statistiche_aggregate_admin AS
SELECT
    P.Anno,
    P.Mese,
    COUNT(*) AS Numero_Transazioni,
    SUM(CASE WHEN T.TipoTransazione = 'S'
             THEN T.Importo ELSE 0 END) AS Totale_Spese,
    SUM(CASE WHEN T.TipoTransazione = 'E'
             THEN T.Importo ELSE 0 END) AS Totale_Entrate
FROM TRANSIZIONE T
JOIN PERIODO P ON T.ID_Periodo = P.ID_Periodo
GROUP BY P.Anno, P.Mese;
\end{lstlisting}

\begin{lstlisting}[caption={Vista dello stato dei budget}]
CREATE VIEW v_budget_stato AS
SELECT
    B.ID_Budget,
    B.Email,
    P.Mese,
    P.Anno,
    COALESCE(C.Nome, 'Budget globale') AS Ambito,
    B.Importo_Limite,
    COALESCE(SUM(T.Importo), 0) AS Totale_Speso,
    B.Importo_Limite - COALESCE(SUM(T.Importo), 0) AS Residuo,
    CASE WHEN COALESCE(SUM(T.Importo), 0) > B.Importo_Limite
         THEN TRUE ELSE FALSE END AS Superato
FROM BUDGET B
JOIN PERIODO P ON B.ID_Periodo = P.ID_Periodo
LEFT JOIN CATEGORIA C ON B.ID_Categoria = C.ID_Categoria
LEFT JOIN TRANSIZIONE T
    ON T.Email = B.Email
   AND T.ID_Periodo = B.ID_Periodo
   AND T.TipoTransazione = 'S'
   AND (B.ID_Categoria IS NULL OR T.ID_Categoria = B.ID_Categoria)
GROUP BY B.ID_Budget, B.Email, P.Mese, P.Anno,
         C.Nome, B.ID_Categoria, B.Importo_Limite;
\end{lstlisting}

\subsection{Migrazione di un database esistente}
Lo script \path{doc/sql/03_migrazione_database_esistente.sql} aggiorna in modo incrementale le installazioni create con versioni precedenti. Prima di ogni modifica consulta \texttt{INFORMATION\_SCHEMA}; in questo modo aggiunge soltanto colonne, vincoli e indici ancora assenti. \section{Progettazione dell’applicazione}
\subsection{Architettura generale dell’applicazione}
L'applicazione S.A.G.E. è un programma desktop organizzato secondo un'architettura a livelli. La separazione delle responsabilità evita che l'interfaccia grafica esegua direttamente le query e rende più semplice modificare una parte del sistema senza intervenire sulle altre. Il flusso ordinario è il seguente:

\begin{center}
\texttt{View $\rightarrow$ Controller $\rightarrow$ Service $\rightarrow$ DAO $\rightarrow$ MySQL}
\end{center}

Le classi del livello \texttt{view} raccolgono gli input e aggiornano le schermate; i controller espongono le operazioni richieste dall'interfaccia; i service applicano le regole di dominio e coordinano le transazioni; i DAO contengono il codice JDBC e traducono le righe del database in oggetti del model. Le classi del package \texttt{model} rappresentano invece gli oggetti persistenti, come utente, transazione, budget, categoria, documento e spesa ricorrente.

La finestra principale \texttt{MainFrame} utilizza un \texttt{CardLayout}. All'avvio mostra il pannello di autenticazione; dopo il login crea una dashboard diversa in base al ruolo dell'utente. Un account con ruolo \texttt{UTENTE} accede alla dashboard personale, mentre un account con ruolo \texttt{ADMIN} accede alla dashboard amministrativa. Il database risiede in locale e viene raggiunto direttamente dall'applicazione, realizzando quindi un'architettura desktop 2-tier.

\subsection{Tecnologie usate}
Le tecnologie principali sono:
\begin{itemize}
    \item \textbf{Java SE}: linguaggio usato per logica applicativa, accesso ai dati e interfaccia;
    \item \textbf{Java Swing e AWT}: costruzione delle finestre, dei form, delle tabelle, dei pannelli e dei grafici;
    \item \textbf{JDBC}: collegamento al DBMS e gestione di query parametrizzate e transazioni;
    \item \textbf{MySQL Connector/J}: driver JDBC incluso nella cartella \path{lib};
    \item \textbf{MySQL}: DBMS utilizzato per la persistenza dei dati;
    \item \textbf{XAMPP}: ambiente locale usato per eseguire MySQL, gestire l'avvio del servizio e amministrare il database tramite phpMyAdmin;
    \item \textbf{SQL}: definizione dello schema, trigger, viste, popolamento e interrogazioni;
    \item \textbf{API Desktop di Java}: apertura dei documenti digitali con il programma predefinito del sistema operativo.
\end{itemize}
Non viene utilizzato un ORM: la traduzione tra oggetti Java e relazioni è gestita esplicitamente dai DAO. Questa scelta rende visibili le query effettivamente eseguite ed è coerente con gli obiettivi del corso.

\subsection{Collegamento al database tramite JDBC}
La classe \texttt{DatabaseConnection} centralizza la creazione delle connessioni. Prima carica il driver \texttt{com.mysql.cj.jdbc.Driver}, quindi usa \texttt{DriverManager.getConnection}. Il server MySQL viene avviato localmente tramite XAMPP; in assenza di configurazioni esterne, il collegamento predefinito punta al database locale:

?serverTimezone=Europe/Rome

URL, utente e password possono essere sovrascritti tramite proprietà Java o variabili d'ambiente: \texttt{sage.db.url}, \texttt{sage.db.user}, \texttt{sage.db.password} oppure \texttt{SAGE\_DB\_URL}, \texttt{SAGE\_DB\_USER}, \texttt{SAGE\_DB\_PASSWORD}. Le connessioni, i \texttt{PreparedStatement} e i \texttt{ResultSet} sono chiusi con \emph{try-with-resources}. Le query ricevono i dati attraverso parametri, evitando la concatenazione di stringhe. Le operazioni che coinvolgono più relazioni, come inserimento di una spesa, aggiornamento dei budget e generazione delle ricorrenze, disabilitano temporaneamente l'auto-commit e terminano con \texttt{commit}; in caso di errore viene eseguito il \texttt{rollback}.

\texttt{MovimentiController}, \texttt{MovimentiService} & Inserimento, modifica, eliminazione e ricerca delle transazioni e delle classificazioni personali. \\
\texttt{BudgetController}, \texttt{BudgetService} & Creazione o aggiornamento dei budget e calcolo dello stato di utilizzo. \\
\texttt{SpeseRicorrentiController}, \texttt{SpeseRicorrentiService} & Gestione dei modelli ricorrenti e generazione delle transazioni mancanti fino alla data corrente. \\
\texttt{DocumentiController}, \texttt{DocumentiPanel} & Associazione, modifica, eliminazione e apertura dei documenti collegati alle spese. \\
\texttt{DashboardDataService}, \texttt{DashboardOverviewCalculator} & Raccolta dei dati necessari al riepilogo e calcolo di saldi e aggregazioni mostrate nei grafici. \\
\texttt{Jdbc*DAO} & Esecuzione delle query SQL e conversione dei risultati negli oggetti del model. \\
\bottomrule
\end{longtable}

Le classi model non dipendono da Swing né da JDBC. Tale indipendenza permette di utilizzare gli stessi oggetti sia nelle viste sia nei servizi e semplifica i test della logica di calcolo.

\subsection{Gestione degli errori e validazione input}
La validazione è distribuita su più livelli:
\begin{itemize}
    \item i form Swing verificano campi obbligatori, importi positivi, date e selezioni richieste;
    \item i service applicano regole di dominio, come unicità dei nomi disponibili, frequenza positiva delle ricorrenze e coerenza tra data iniziale, prossima scadenza e data finale;
    \item i DAO usano query parametrizzate e filtrano sempre per l'email dell'utente quando trattano dati personali;
    \item il DBMS applica chiavi esterne, \texttt{CHECK}, \texttt{UNIQUE}, trigger e vincoli di proprietà.
\end{itemize}

Gli errori di input vengono rappresentati principalmente con \texttt{IllegalArgumentException}; gli errori di accesso ai dati propagano una \texttt{SQLException}. Le viste intercettano tali eccezioni e mostrano messaggi mediante \texttt{JOptionPane}. Prima delle eliminazioni viene richiesta una conferma esplicita. I documenti sono controllati sia prima della registrazione sia prima dell'apertura, così da gestire il caso in cui il file sia stato spostato o cancellato.

Le operazioni più lente, come login, caricamento dei documenti e configurazione iniziale, usano \texttt{SwingWorker}: il lavoro JDBC viene eseguito fuori dall'Event Dispatch Thread e l'interfaccia resta utilizzabile. La password non viene salvata in chiaro, ma confrontata e registrata mediante \texttt{SHA2} nel database.

\subsection{Interfaccia grafica Java Swing}
L'interfaccia è realizzata interamente in Swing. Un tema comune definisce font, spaziature e componenti; la sidebar permette di cambiare area senza aprire nuove finestre. La dashboard dell'utente utilizza pannelli a scheda per mostrare saldo, entrate, spese e percentuale di budget utilizzato. I grafici sono disegnati da componenti dedicati e si aggiornano quando l'utente seleziona il filtro mese, anno o intero storico.

Le principali aree disponibili all'utente sono:
\begin{itemize}
    \item \textbf{Riepilogo}: indicatori, andamento temporale, distribuzione per categoria, stato dei budget e ultimi movimenti;
    \item \textbf{Transazioni}: schede delle entrate e delle spese, con modifica ed eliminazione;
    \item \textbf{Budget}: visualizzazione dei budget unici tramite barre di avanzamento, con modifica, eliminazione e creazione di nuovi limiti tramite il pulsante \emph{+ Budget};
    \item \textbf{Categorie e Tag} e \textbf{Fonti}: elementi di sistema e personali, con scelta o caricamento di un'icona e pulsanti di modifica/eliminazione;
    \item \textbf{Ricorrenze}: modelli periodici e consultazione delle spese generate;
    \item \textbf{Documenti}: documenti collegati alle spese, apribili con il programma predefinito.
\end{itemize}

La dashboard amministrativa è separata da quella personale. Mostra numero di utenti, numero di transazioni, spese, entrate, budget superati, andamento mensile globale e categorie più utilizzate. I dati sono aggregati: l'amministratore non accede alle descrizioni dei movimenti né ai documenti personali.

\subsection{Flussi d’uso principali}
\begin{enumerate}
    \item \textbf{Registrazione e login}: lo studente crea un account, accede con email e password e viene indirizzato alla propria dashboard; il ruolo amministrativo apre invece la vista aggregata.
    \item \textbf{Inserimento di una spesa}: l'utente specifica importo, data, descrizione e categoria, seleziona eventuali tag e documento; il sistema registra il periodo e aggiorna i budget interessati nella stessa transazione JDBC.
    \item \textbf{Inserimento di una entrata}: l'utente seleziona una fonte; la transazione viene salvata senza categoria, tag o documento.
    \item \textbf{Definizione di un budget}: l'utente apre il form tramite \emph{+ Budget}, sceglie limite ed eventuale categoria; se esiste già un budget per lo stesso ambito, il sistema lo aggiorna invece di crearne una copia. Il totale speso viene ricalcolato sui movimenti del mese corrente e la schermata mostra la barra di avanzamento aggiornata.
    \item \textbf{Gestione delle classificazioni}: categorie, tag e fonti personali possono essere creati, modificati o eliminati; nella versione dimostrativa sono esposti anche i pulsanti di modifica ed eliminazione sugli elementi di sistema, restando comunque attivi i vincoli referenziali del database.
    \item \textbf{Spesa ricorrente}: il modello memorizza nome, importo, frequenza, categoria e scadenze; il servizio genera le transazioni non ancora registrate e ne evita la duplicazione.
    \item \textbf{Documento digitale}: l'utente seleziona una spesa priva di allegato e un file locale; il DB conserva il percorso e l'interfaccia permette successivamente di aprirlo, modificarlo o eliminarlo.
    \item \textbf{Statistiche amministrative}: l'amministratore consulta indicatori e grafici costruiti su dati aggregati e gestisce categorie, tag e fonti di sistema.
\end{enumerate}

\subsection{Errori noti o limitazioni}
La principale limitazione riguarda i documenti: il DB conserva il percorso del file, non il contenuto. Se il file viene spostato, cancellato o se l'utente usa un altro dispositivo, il percorso può risultare non valido. Questa scelta è consapevole e motivata dalla semplicità del progetto e dal minor carico sul database.

\section{Conclusioni}
\subsection{Risultato ottenuto}
Il progetto realizza una base di dati relazionale coerente con il dominio della gestione economica personale. L'applicazione Java consente di autenticare un utente, mantenere una sessione, interrogare dati filtrati per email e visualizzare le principali aree funzionali.

\subsection{Scelte progettuali principali}
Le scelte più rilevanti sono il collasso della gerarchia spesa/entrata in \textsc{TRANSIZIONE}, l'isolamento dati tramite email, la modellazione ibrida di elementi globali/personali, la ridondanza controllata del budget e la memorizzazione dei documenti tramite path.

\subsection{Possibili sviluppi futuri}
Sviluppi futuri includono:
\begin{itemize}
    \item sincronizzazione o copia controllata dei documenti in una cartella applicativa;
    \item eventuale uso di \texttt{LONGBLOB} per rendere i documenti portabili attraverso il solo database;
    \item completamento delle funzionalità amministrative;
    \item grafici statistici più avanzati;
    \item esportazione dei report in PDF o CSV.
\end{itemize}
